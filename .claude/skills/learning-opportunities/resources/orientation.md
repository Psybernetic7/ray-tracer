# Repo Orientation: ray_tracing

> Generated by /orient. Re-run to update.

## One-line purpose
A minimal CPU ray tracer, following *Ray Tracing in One Weekend*. It renders one sphere, shaded by its surface normals, against a black-to-orange gradient background and writes the result as a plain-text PPM image to stdout.

## Primary language(s)
- C++ (header-only helpers + single `main.cc`; no build system, compiled directly, e.g. `g++ main.cc -o main && ./main > image.ppm`)

## Pipeline / workflow stages
1. **Image setup**: pick the aspect ratio and width, then derive the height (`main.cc` "Image" section).
2. **Camera/viewport setup**: define a virtual viewport 1 unit in front of the camera, plus the per-pixel step vectors (`pixel_delta_u/v`, `pixel00_loc`).
3. **Ray generation**: for each pixel (row `j`, column `i`), build a ray from the camera center through the pixel center.
4. **Shading**: `ray_color` tests the ray against the sphere (`hit_sphere`). A hit is colored by the surface normal; a miss gets the background gradient.
5. **Output**: `write_color` converts [0,1] floats to 0–255 ints and streams a PPM line. Progress goes to `std::clog` (stderr).

## Key files
- `main.cc`: camera setup, render loop, `hit_sphere`, `ray_color` | the whole program flow lives here
- `vec3.h`: 3D vector class + operators (`dot`, `cross`, `unit_vector`) | the math vocabulary everything else uses
- `ray.h`: `ray` = origin + t·direction, with `at(t)` | the core abstraction of ray tracing
- `color.h`: `color` alias and `write_color` | how numbers become pixels
- `image.ppm`: rendered output | open it in an image viewer to check your mental model
- `walkthrough-main-l37-59.html`: earlier generated explainer for the camera setup | review aid

## Core concepts
**Ray as a parametric line**: P(t) = A + t·b. `ray::at` in `ray.h`. `t` measures distance along the ray, and only t > 0 is "in front of" the camera.
**Viewport**: an imaginary rectangle in 3D space that the pixel grid maps onto. `main.cc` lines 46–62. Note that `viewport_v` points *down* (−y) because image rows increase downward.
**Ray–sphere intersection**: solve the quadratic |P(t) − C|² = r². `hit_sphere` uses the simplified `h = b·(C−O)` form. The discriminant tells you whether the ray hits; the returned root is the nearest hit.
**Type aliases for meaning**: `point3` and `color` are both just `vec3`. They document intent but give no type safety.
**PPM format**: a text header `P3 / width height / 255` followed by one "r g b" line per pixel.

## Common gotchas
- The compiler won't stop you from mixing up `point3`/`color`/`vec3`; they're the same type.
- `write_color` doesn't clamp. Values above 1.0 produce bytes above 255 and a corrupt image.
- stdout is the image and stderr is the progress. Redirect only stdout (`./main > image.ppm`), or the progress text ends up inside the image.
- `hit_sphere` returns `-1.0` as a "miss" sentinel, and `ray_color` checks `t > 0.0`. Hits behind the camera are therefore treated as misses.

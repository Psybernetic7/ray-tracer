# Repo Orientation: ray_tracing

> Generated by /orient. Re-run to update.

## One-line purpose
A minimal CPU ray tracer following *Ray Tracing in One Weekend*. It renders a small sphere resting on a huge "ground" sphere, shaded by surface normals against a black-to-orange sky gradient, and writes a plain-text PPM image to stdout.

## Primary language(s)
- C++ (header-only classes plus a single `main.cc`; no build system, compiled directly, e.g. `g++ main.cc -o main && ./main > image.ppm`)

## Pipeline / workflow stages
1. **Image setup**: pick aspect ratio and width, derive height (`main.cc`, "Image").
2. **World setup**: build a `hittable_list` and `add` two `sphere`s (`main.cc`, "World").
3. **Camera/viewport setup**: viewport 1 unit in front of the camera, plus per-pixel step vectors.
4. **Ray generation**: for each pixel, build a `ray` from the camera center through the pixel center.
5. **Shading**: `ray_color` asks `world.hit(...)` for the nearest hit. A hit is colored from `rec.normal`; a miss gets the sky gradient.
6. **Output**: `write_color` converts [0,1] floats to 0–255 ints and prints a PPM line. Progress goes to stderr via `std::clog`.

## Key files
- `main.cc`: world, camera, render loop, `ray_color` | the whole program flow
- `hittable.h`: `hit_record` (hit point, normal, `t`, `front_face`) and the abstract `hittable` interface | the contract every object must satisfy
- `sphere.h`: `sphere` implements `hittable::hit` with the ray-sphere quadratic | where the intersection math now lives
- `hittable_list.h`: a `hittable` that holds many `hittable`s and returns the closest hit | how multiple objects become one "world"
- `interval.h`: `interval(min, max)` with `contains`/`surrounds` | the valid range of `t` for a hit
- `rtheader.h`: shared includes, `infinity`, `pi`, `shared_ptr` using-declarations | the single include that pulls in the basics
- `vec3.h`: 3D vector class and operators (`dot`, `cross`, `unit_vector`) | the math vocabulary
- `ray.h`: `ray` = origin + t·direction, with `at(t)` | the core abstraction

## Core concepts
**Ray as a parametric line**: P(t) = A + t·b. `ray::at` in `ray.h`. Only `t` inside the allowed interval counts as a hit.
**Abstract interface / polymorphism**: `hittable` declares `virtual bool hit(...) const = 0`. `sphere` and `hittable_list` both override it, so `ray_color` can call `world.hit` without knowing what's inside. See `hittable.h`.
**Closest-hit search**: `hittable_list::hit` shrinks `closest_so_far` after each hit, so later objects only count if they are nearer. See `hittable_list.h`.
**Outward vs. front-face normals**: `set_face_normal` in `hittable.h` stores a normal that always opposes the ray and records which side was hit in `front_face`.
**Shared ownership**: objects are held as `shared_ptr<hittable>` (created with `make_shared`), so the list can hold different shape types by pointer.

## Common gotchas
- `hit_record` is an *output parameter*: `hit(..., hit_record& rec)` fills `rec` and returns only a bool. `hittable_list::hit` uses `temp_rec` so a later miss can't clobber a good `rec`.
- Header order matters. `hittable.h`, `interval.h` and `sphere.h` have no includes of their own for `ray`, `interval` or `infinity`. They compile only because `rtheader.h` is included first in `main.cc`.
- `point3` and `color` are both aliases of `vec3`, so the compiler won't catch mixing them up.
- `write_color` doesn't clamp, so values above 1.0 produce bytes above 255.

## Suggested exercise sequence
1. **Read the interface, then explain the design.** Open `hittable.h` and `hittable_list.h`. Then explain in your own words: why can `ray_color` call `world.hit(...)` without knowing that the world contains spheres? What would you need to write to add a new shape?
2. **Follow one hit through `sphere.h`.** Open `sphere.h` and read `hit`. What are the two conditions under which it returns `false`, and which fields of `rec` does it fill in when it returns `true`?
